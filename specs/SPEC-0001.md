## Abstract

Defines the canonical format for all Eureka SPECs, the status lifecycle, and the process agents and humans MUST follow when creating or amending a SPEC.

## Specification

### Format

Every SPEC MUST begin with a level-1 heading of the form `# SPEC-NNNN: Title`.

Every SPEC MUST contain a metadata table immediately after the heading with exactly these fields: `Status`, `Type`, `Created`, `Requires`, `Supersedes`. No additional fields are permitted in the metadata table.

`Status` MUST be one of: `Draft`, `Review`, `Active`, `Superseded`, `Deprecated`.

`Type` MUST be one of: `Core`, `Interface`, `Informational`, `Process`.

`Created` MUST be an ISO 8601 date (`YYYY-MM-DD`).

`Requires` MUST list every SPEC that MUST be understood before this SPEC can be applied, as a comma-separated list of `SPEC-NNNN` identifiers, or the literal `None`.

`Supersedes` MUST name the SPEC this document replaces, or the literal `None`.

Every SPEC MUST contain the following sections in order: `## Abstract`, `## Specification`. The sections `## Rationale` and `## Reference Implementation` MAY be present and MUST appear after `## Specification` if present. No other top-level sections are permitted.

`## Abstract` MUST be a single paragraph.

`## Specification` MUST use RFC 2119 normative keywords: **MUST** / **MUST NOT** (absolute), **SHOULD** / **SHOULD NOT** (strong recommendation), **MAY** (optional).

`## Reference Implementation` MUST contain only file paths and line references. It MUST NOT contain prose descriptions of behavior.

### Numbering

SPEC numbers MUST be four-digit zero-padded integers assigned sequentially from `0001`. Numbers MUST NOT be reused after a SPEC is deprecated or superseded.

### Status lifecycle

A new SPEC MUST be created with `Status: Draft`. Agents MUST NOT set status to anything other than `Draft` without explicit human instruction.

The transition sequence is: `Draft` → `Review` → `Active`. A human MUST approve each transition.

An `Active` SPEC MAY be moved to `Superseded` when a new SPEC replaces it. The superseding SPEC MUST reference the old one in its `Supersedes` field. An `Active` SPEC MAY be moved to `Deprecated` when it is retired with no replacement.

### Binding authority

Only SPECs with `Status: Active` are normatively binding on agent and human behavior. Draft and Review SPECs are proposals and MUST NOT be treated as requirements.

### Writing a SPEC

An agent writing a SPEC MUST derive all normative statements by reading the relevant source files directly. The agent MUST NOT source normative content from documentation files, existing docs, README prose, or code comments.

An agent MUST set `Status: Draft` on any SPEC it creates or amends.

### Amending a SPEC

When a code change requires amending an Active SPEC, the amendment MUST be committed in the same commit as the code change. If the amendment is substantial (adds, removes, or modifies MUST/MUST NOT statements), the agent MUST move the SPEC back to `Draft` and wait for human promotion to `Active`.

### Index

`specs/README.md` MUST be kept up to date with a table mapping every source module or file to the SPEC(s) that govern it. When a new SPEC is created, the index MUST be updated in the same commit.
