# SPEC-0020: Agent Hook Integration

| Field      | Value                        |
|------------|------------------------------|

## Abstract

Defines the `HookSpec` YAML declaration, the subprocess I/O protocol for
agent hooks, and the `SubprocessHook` Rust type that bridges the two. A hook
is a subprocess invoked synchronously at observable points of an agent's rig
prompt loop — before a model call, around tool calls, and after turns. Hooks
can observe, steer, or terminate the loop by returning a structured `Flow`
response. They compose with Eureka's existing built-in hooks and with each
other via rig-core's `HookStack`.

## Specification

### HookSpec

`HookSpec` declares one subprocess-backed agent hook. It MUST contain:

- `name: String` — unique name within the agent; used only for logging
- `command: Vec<String>` — subprocess argv; `command[0]` is the binary
- `events: Vec<String>` — event filter; see **Supported Events** below;
  an empty list means all supported events are dispatched
- `timeout_secs: u32` — per-invocation wall-clock limit; defaults to `5`

`description: Option<String>` MAY be present.

### AgentSpec amendment

`AgentSpec` (SPEC-0008) MUST be extended with:

- `hooks: Vec<HookSpec>` — hooks attached to this agent; defaults to empty

Path resolution for `HookSpec.command[0]` follows the same rule as
`ToolSpec.command[0]` (SPEC-0008 §Path resolution): relative paths that
resolve to an existing file are made absolute; bare binary names are left
unchanged for PATH lookup at spawn time.

### Supported Events

The following event names MAY appear in `HookSpec.events`. The set is
restricted to events that are safe to dispatch to a subprocess — streaming
delta events (`text_delta`, `tool_call_delta`, `stream_response_finish`) are
excluded because their per-token frequency makes subprocess round-trips
prohibitive.

| Event name            | rig `StepEvent` variant       | Observe-only? |
|-----------------------|-------------------------------|---------------|
| `completion_call`     | `StepEvent::CompletionCall`   | No            |
| `completion_response` | `StepEvent::CompletionResponse` | Yes         |
| `model_turn_finished` | `StepEvent::ModelTurnFinished`| Yes           |
| `tool_call`           | `StepEvent::ToolCall`         | No            |
| `tool_result`         | `StepEvent::ToolResult`       | No            |
| `invalid_tool_call`   | `StepEvent::InvalidToolCall`  | No            |

Observe-only events MUST return `continue` or `terminate`. Attempting to
return a steering flow for an observe-only event is a protocol error (see
**Error handling**).

### Subprocess I/O Protocol

The hook subprocess is spawned fresh for each invocation. The scheduler MUST
write one JSON object to the subprocess's stdin followed by a newline, then
read one JSON response line from stdout. The subprocess MUST exit after
writing its response. Interaction with stderr is not defined; implementations
SHOULD forward it to the host process log at `WARN` level.

#### Input schema

```json
{
  "event":   "<event_name>",
  "<field>": <value>,
  ...
}
```

Per-event fields:

**`completion_call`**
```json
{ "event": "completion_call", "turn": 1, "prompt": "<message text>",
  "history_len": 3 }
```

**`completion_response`**
```json
{ "event": "completion_response", "turn": 1, "prompt": "<message text>" }
```

**`model_turn_finished`**
```json
{ "event": "model_turn_finished", "turn": 1,
  "input_tokens": 512, "output_tokens": 128, "total_tokens": 640 }
```

**`tool_call`**
```json
{ "event": "tool_call", "tool_name": "search_literature",
  "tool_call_id": "<id or null>", "internal_call_id": "<id>",
  "args": "{\"query\": \"...\"}" }
```

**`tool_result`**
```json
{ "event": "tool_result", "tool_name": "search_literature",
  "tool_call_id": "<id or null>", "internal_call_id": "<id>",
  "args": "{\"query\": \"...\"}",
  "result": "<tool output string>",
  "outcome": "success" | "error" | "skipped" | "denied" }
```

**`invalid_tool_call`**
```json
{ "event": "invalid_tool_call", "tool_name": "<attempted name>",
  "args": "<raw args string>", "reason": "<why it is invalid>" }
```

#### Output schema

The subprocess MUST write one JSON object. The `flow` field selects the
action. All other fields are optional and event-dependent.

**`continue`** — proceed normally (valid for all events)
```json
{ "flow": "continue" }
```

**`terminate`** — end the agent run early (valid for all events)
```json
{ "flow": "terminate", "reason": "budget exceeded" }
```

**`skip`** — return `reason` as the tool result without executing the tool
(valid for `tool_call` and `invalid_tool_call`)
```json
{ "flow": "skip", "reason": "tool denied by policy" }
```

**`rewrite_args`** — execute the tool with replacement arguments
(valid for `tool_call` only)
```json
{ "flow": "rewrite_args", "args": { "query": "sanitized query" } }
```

**`rewrite_result`** — replace the tool output the model sees
(valid for `tool_result` only)
```json
{ "flow": "rewrite_result", "result": "<truncated or redacted output>" }
```

**`patch_request`** — patch this turn's model request before it is sent
(valid for `completion_call` only). All patch fields are optional; omitted
fields inherit the agent's configured value.
```json
{
  "flow": "patch_request",
  "preamble":          "<optional system prompt override>",
  "temperature":       0.3,
  "max_tokens":        1024,
  "active_tools":      ["tool_a", "tool_b"],
  "extra_context":     [{ "id": "doc1", "text": "..." }],
  "additional_params": { "provider_specific_key": "value" }
}
```

**`retry`** — re-prompt with corrective feedback
(valid for `invalid_tool_call` only)
```json
{ "flow": "retry", "feedback": "The tool 'foo' does not exist. Use 'bar'." }
```

### SubprocessHook

`SubprocessHook` is a Rust struct that implements `AgentHook<M>` for any
`M: CompletionModel`. It MUST:

- Store `name: String`, `command: Vec<String>`, `events: HashSet<String>`,
  `timeout_secs: u32`, and `work_dir: PathBuf`
- In `observes(&self, kind: StepEventKind) -> bool`: return `false` for
  `TextDelta`, `ToolCallDelta`, and `StreamResponseFinish` unconditionally;
  for other kinds, return `true` if `events` is empty or contains the
  corresponding event name string
- In `on_event`: serialize the event to the input JSON schema, spawn
  `command[0]` with `command[1..]` as arguments, set `current_dir` to
  `work_dir`, write the JSON + newline to stdin, read one line from stdout,
  and deserialize the `Flow` response
- If the subprocess exceeds `timeout_secs`, log a warning and return
  `Flow::Continue` — a hook timeout MUST NOT terminate or fail the agent run
- If the subprocess exits with a non-zero status, produces no stdout, or
  produces malformed JSON, log a warning and return `Flow::Continue`
- Protocol errors (unsupported flow for the event type) are treated as
  `Flow::Continue` with a warning log
- `SubprocessHook` MUST be `Send + Sync`

### session/builder integration

`Session` builder (`SessionBuilder`) constructs `SubprocessHook` instances
from each `HookSpec` in an `AgentSpec` and attaches them to the agent's
prompt request via `add_hook`. Hooks are attached in declaration order.
The existing built-in hooks (`UsageHook`, `LiveCounterHook`,
`ToolEventHook`) are attached after user-declared hooks.

### Filesystem convention

The `hooks/` directory adjacent to `tools/` in a graph package is the
RECOMMENDED location for hook scripts. It is a convention only; paths in
`command` are resolved per the path resolution rule and MAY point anywhere.

## Rationale

The subprocess model mirrors the existing `ToolSpec` pattern, giving graph
authors a familiar zero-compile-time extension point. The restricted event
set (no streaming deltas) is intentional: a subprocess round-trip at token
frequency would stall the model stream. The `observes` guard ensures
streaming-heavy runs pay no dispatch overhead for hooks that don't care about
deltas.

Returning `Flow::Continue` on all subprocess failures keeps the hook
integration non-fatal by default — consistent with how RAG failures, MCP
connection drops, and tool timeouts are handled throughout Eureka.
