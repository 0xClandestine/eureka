# SPEC-0021: MCP Tool Integration

| Field      | Value       |
|------------|-------------|
| Status     | Draft       |
| Type       | Interface   |
| Created    | 2026-07-14  |
| Requires   | SPEC-0008, SPEC-0010 |
| Supersedes | None        |

## Abstract

Defines how LLM agents in Eureka declare and consume tools served by Model
Context Protocol (MCP) servers. MCP tools are discovered at session build time,
registered on the rig `AgentBuilder` alongside existing `CommandTool`s, and
made available to the agent loop without changes to the loop itself. This
enables agents to use any MCP-compliant server — including filesystem, shell,
code-execution, and proof-assistant servers — without Eureka implementing those
capabilities directly.

## Specification

### Manifest schema — `mcp_servers`

An `AgentSpec` MAY declare a list of MCP servers under the key `mcp_servers`.
Each entry MUST contain:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Unique label for this server within the agent. Used in logs and error messages. MUST NOT be empty. |
| `transport` | string enum | yes | `"stdio"` or `"http"`. |
| `command` | array of strings | when `transport = "stdio"` | Argv for the server subprocess. `command[0]` is the binary. MUST contain at least one element. |
| `env` | map of string→string | no (`stdio` only) | Extra environment variables injected into the `stdio` subprocess. Merged on top of the inheriting process environment. Defaults to empty. |
| `uri` | string | when `transport = "http"` | Full HTTP URI of the MCP server (e.g. `"http://localhost:8080"`). |

A `stdio` entry MUST supply `command` and MUST NOT supply `uri`.
An `http` entry MUST supply `uri` and MUST NOT supply `command`.
`env` is only meaningful for `stdio` entries; it MUST be ignored for `http` entries.

Example:

```yaml
agents:
  - id: generation
    mcp_servers:
      - name: lean-lsp
        transport: stdio
        command: [uvx, lean-lsp-mcp]
        env:
          LEAN_MCP_DISABLED_TOOLS: lean_run_code,lean_multi_attempt
      - name: lean4
        transport: http
        uri: "http://localhost:9000"
    tools: [*arxiv_search, *context_store]
```

### Runtime types

`McpServerSpec` (in `manifest/agent.rs`) mirrors the YAML shape above.

`McpServerDef` (in `agent/def.rs`) is the resolved runtime counterpart, added
to `AgentDef`:

```rust
pub struct AgentDef {
    // existing fields ...
    pub mcp_servers: Vec<McpServerDef>,
}

pub struct McpServerDef {
    pub name: String,
    pub transport: McpTransport,
}

pub enum McpTransport {
    Stdio { command: Vec<String>, env: HashMap<String, String> },
    Http  { uri: String },
}
```

`AgentSpec::resolve_paths` MUST resolve the `command[0]` binary of `stdio`
servers against the manifest base directory, following the same rule as
`ToolSpec`: if the resolved path exists on disk the path is rewritten to
absolute; if it does not exist the token is left unchanged so `PATH` lookup
applies at spawn time.

### Connection lifecycle

MCP server connections are established inside `SessionBuilder::build_agent_node`
before the `RigClient` is constructed, not during agent activation.

For each `McpServerDef` in `AgentDef.mcp_servers`:

1. **`stdio` transport** — spawn the command as a child process using
   `tokio::process::Command`. MUST set `current_dir` to `graph_dir`.
   MUST inject all key-value pairs from `McpTransport::Stdio::env` into the
   subprocess environment via `.envs(env)`. Construct an
   `rmcp::transport::TokioChildProcess` transport from the child.

2. **`http` transport** — construct an
   `rmcp::transport::StreamableHttpClientTransport` from the URI.

3. In both cases, call `ClientInfo::serve(transport).await` to obtain the MCP
   service handle, then call `handle.list_tools(Default::default()).await` to
   retrieve the tool list.

4. If connection or tool listing fails, `build_agent_node` MUST return
   `Err(EngineError::NodeCreation(...))`. Failures are not retried.

5. The resulting `(tools, peer, Option<Child>)` triple is stored in an
   `McpConnection` value held by the `RigClient`:

```rust
struct McpConnection {
    tools: Vec<rmcp::model::Tool>,
    peer:  rmcp::service::Peer<rmcp::RoleClient>,
    child: Option<tokio::process::Child>,  // stdio only
}
```

**Session shutdown**: when the `Session` is dropped, every `stdio` child
process MUST be killed. The `RigClient` SHOULD implement `Drop` to send
`SIGKILL` to all child processes it holds. If `kill()` returns an error it
MUST be logged at `warn` level and otherwise ignored — shutdown MUST NOT panic.

### Agent loop integration

In `RigClient::run_agent_loop_with_environment`, after building the
`AgentBuilder` and registering `CommandTool`s but before calling `.build()`,
the implementation MUST call `.rmcp_tools(conn.tools.clone(), conn.peer.clone())`
for each `McpConnection`:

```rust
for conn in &self.mcp {
    builder = builder.rmcp_tools(conn.tools.clone(), conn.peer.clone());
}
let agent = builder.tool(submit).tools(command_tools).build();
```

MCP tools are additive to `CommandTool`s. The agent sees both sets in its tool
schema.

### Name collision rules

The name `"submit"` is reserved. `SessionBuilder::build_agent_node` MUST
return `Err(EngineError::NodeCreation(...))` if any MCP server exposes a tool
named `"submit"` (case-insensitive comparison).

If a `CommandTool` and an MCP tool share the same name, `build_agent_node`
MUST return `Err(EngineError::NodeCreation(...))`. Names MUST be unique across
all tool sources for a given agent.

### Tool name visibility

`build_preamble` in `agent/client.rs` currently constructs the tool name list
from `CommandTool`s only. When MCP connections are present, the preamble MUST
also include the names of all MCP tools so the agent is aware of them at the
start of its loop.

### Dependencies

`rig-core` MUST be compiled with the `rmcp` feature enabled.
The `rmcp` crate MUST be added as a direct dependency of the `eureka` crate
with at least the `client` feature enabled.

### Agent-level opt-in

`mcp_servers` defaults to an empty list. Agents that do not declare
`mcp_servers` are unaffected by this feature and MUST behave identically to
their pre-SPEC-0021 behaviour.

## Rationale

**Connection at build time, not activation time.** Establishing an MCP
connection on every agent activation would add latency and spawn redundant
processes per round. Connecting once and caching the peer handle amortises
the cost across all activations of that agent within a session.

**`stdio` vs `http` as the only two transports.** The `rmcp` crate supports
both. `stdio` covers local processes (filesystem servers, code interpreters,
Lean4 checkers) without requiring a listening port. `http` covers remote or
long-lived servers. Websocket and SSE transports are not included in this SPEC;
they MAY be added by a later SPEC if needed.

**No workspace path in `RunEnvironment`.** A dedicated workspace abstraction
is not required because MCP filesystem servers accept a root directory at
launch time (via `command` arguments for `stdio` servers). The session startup
code MAY create and pass a session-scoped directory as a command argument; this
is an operational concern, not a protocol one, and is outside the scope of this
SPEC.

**Name collision as a hard error.** Silent shadowing (where one tool silently
overrides another with the same name) produces confusing agent behaviour that
is difficult to debug. Failing fast at build time is the correct trade-off.
