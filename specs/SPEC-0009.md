## Abstract

Defines the event-driven scheduler: activation lifecycle, round semantics, concurrency model, budget backstops, signals, and observable events.

## Specification

### Activation

An activation is the act of calling `Node::process` for one node with its joined inputs. Each activation carries:
- a stable `id: u64` for checkpoint correlation
- `node_id`, `node_kind`, `round`
- `ctx: NodeCtx` with cancellation token and event channel
- `inputs: Vec<PortMsg>` — all available inputs (required + present optional)

A node is activated when all of its required input ports have received artifacts for the current round. Optional input ports that have received artifacts for the current round MUST also be included in `inputs`. Optional ports that have not received artifacts MUST NOT block activation.

The input buffer stores **exactly one artifact per port per `(node_id, round)` key** — a `HashMap<String, Artifact>` keyed by port name. A subsequent delivery to the same `(node_id, port, round)` triple overwrites the prior artifact. Consequently, if a node has a single required input port and N upstream nodes each deliver to that port in the same round, the node is activated N times — once per delivery — each time seeing only the most recently delivered artifact for that port. This is the mechanism that scatter/gather relies on: scatter emits N artifacts to a single required port, triggering N independent activations of the downstream node. Nodes that need to aggregate multiple deliveries (fan-in) MUST use a gather control node backed by a durable store rather than multiple required-port deliveries.

### Round semantics

A round is a monotonically increasing counter (`u32`) starting at `0`.

An artifact emitted on a forward edge (`feedback == false`) MUST be buffered for delivery to the target node in the same round as the emitting activation.

An artifact emitted on a feedback edge (`feedback == true`) MUST be buffered for delivery to the target node in round `N + 1`, where `N` is the round of the emitting activation.

A round is complete when its pending activation count reaches zero. The scheduler MUST then:
1. Check the budget backstops (see below)
2. Advance to the next buffered round
3. Emit a single `CycleCompleted` event for the completed round

`rounds_completed` in `RunStats` counts fully drained cycles, not individual feedback-edge crossings.

### Concurrency

Node activations MUST run as concurrent tokio tasks in a `JoinSet`. The number of simultaneously in-flight activations MUST NOT exceed `SchedulerConfig::max_in_flight` (enforced via a `Semaphore`). The scheduler MUST dispatch new activations as semaphore permits become available.

When the run is cancelled or errors, `JoinSet::abort_all` MUST be called to cancel all in-flight activations.

### Retry behaviour

When a node activation returns an error other than `NodeError::Cancelled`, the scheduler MUST retry the activation up to `SchedulerConfig::max_retries` times before reporting the failure. Each retry attempt acquires and releases the semaphore permit independently (so the permit is not held during the backoff sleep). The delay before attempt `n` (1-indexed) is `min(retry_backoff_ms * 2^(n-1), 30 000)` milliseconds. A `SchedulerEvent::ActivationRetried` event MUST be emitted before each retry.

`NodeError::Cancelled` MUST NOT be retried regardless of `max_retries`.

`NodeError::Agent` errors whose string representation contains `"MaxTurns"` MUST NOT be retried regardless of `max_retries`. These are deterministic turn-budget exhaustions: retrying would burn the same turn budget again and produce an identical failure.

Once all retry attempts are exhausted the scheduler behaves as if no retries were configured: it emits `ActivationFailed`, aborts all in-flight tasks, and returns `SchedulerError::NodeFailed`.

### Budget backstops

The scheduler runs a 100 ms ticker concurrently with the main activation loop. On each tick it MUST call `RunStats::is_budget_exhausted(budget)`. If exhausted, the scheduler MUST emit `RunHalted`, abort in-flight activations, and return successfully with the final `RunStats`. It MUST NOT treat budget exhaustion as an error.

The four backstops are: `total_cost_usd >= max_cost_usd`, `total_tokens >= max_tokens`, `elapsed_secs >= max_wallclock`, `rounds_completed >= max_rounds`.

### Signals

The scheduler MUST accept signals on an `mpsc::Sender<SchedulerSignal>`:
- `Cancel` — gracefully abort the run; activations in flight are cancelled via the `CancellationToken`; the scheduler MUST return `SchedulerError::Cancelled`
- `Pause` — immediately abort in-flight activations and stop dispatching; emit `RunPaused`; the scheduler MUST return `SchedulerError::Paused(stats)` with the current stats
- `Resume` — resume dispatching after a pause

The signal sender MUST remain valid for the lifetime of the scheduler. It MUST NOT be dropped before the scheduler completes.

### SchedulerEvent

The scheduler MUST emit the following events:
- `ActivationStarted { node_id, node_kind, round }` — immediately before `process` is called
- `ActivationCompleted { node_id, node_kind, round, emit_count, inputs, outputs, usage }` — after `process` succeeds; `inputs` is a serialized list of `{port, kind, data}` objects representing what the node received; `outputs` is a serialized list of `{port, kind, data}` objects representing what the node emitted; `usage` is the `NodeUsage` returned by `process` (defaults to zero for events deserialized from older records)
- `ActivationRetried { node_id, node_kind, round, attempt, error }` — before a retry attempt; `attempt` is 1-indexed
- `ActivationFailed { node_id, node_kind, round, error }` — after all retry attempts are exhausted and `process` returns an error
- `CycleCompleted { round }` — after a round's pending count reaches zero
- `ToolCalled { node_id, node_kind, round, tool, args_summary, args }` — when an agent node invokes a shell tool; `args` is the full JSON argument object passed to the tool
- `ToolCompleted { node_id, node_kind, round, tool, result_preview, success }` — after the shell tool subprocess exits; `result_preview` is the first 16,000 characters of stdout (or the error string); `success` is `true` when exit code is 0
- `RunHalted { reason, total_rounds }` — when a budget backstop fires or a halt signal is received
- `RunPaused { round }` — when a pause signal is processed

### SchedulerEvent serialization

`SchedulerEvent` is serialized as a tagged JSON object using `#[serde(tag = "type", rename_all = "camelCase")]`. The `rename_all` attribute applies **only to the variant discriminant** (the `"type"` field value), not to the fields within struct variants. Consequently:

- The `"type"` field value is camelCase: `"activationStarted"`, `"toolCalled"`, `"runHalted"`, etc.
- All fields within struct variants are serialized as snake_case: `node_id`, `node_kind`, `emit_count`, `result_preview`, `total_rounds`, etc.
- Nested structs (e.g. `NodeUsage`) also serialize their fields as snake_case: `total_tokens`, `input_tokens`, `output_tokens`, `cost_usd`.

Consumers of the event stream MUST use snake_case field names when accessing event payload fields.

### SchedulerError

The scheduler MUST return one of:
- `SchedulerError::Cancelled` — run was cancelled
- `SchedulerError::Paused(RunStats)` — run was paused; caller may resume
- `SchedulerError::NodeFailed { node_id, round, error }` — a node activation failed and the run was aborted
- `SchedulerError::NodeNotFound(String)` — a node referenced in the spec has no entry in the registry
- `SchedulerError::Internal(String)` — scheduler internal error
- `SchedulerError::CheckpointMismatch` — a checkpoint does not match the current graph or config identity

### Resumable checkpoints

The scheduler MUST support resuming from a `RunCheckpoint` that encodes the last complete activation snapshot. Identity validation MUST use a stable content hash of both the `GraphSpec` and `EurekaConfig`; if either hash differs from the checkpoint, the scheduler MUST return `SchedulerError::CheckpointMismatch`.

### Live per-request counters

The scheduler MAY carry `live_tokens: Option<Arc<AtomicU64>>` and `live_cost: Option<Arc<Mutex<f64>>>` attached via `with_live_counters()`. When present, these MUST be injected into `NodeCtx` before every activation dispatch so that agents can increment them immediately after each LLM API call, enabling real-time cost/token observability without waiting for `ActivationCompleted` events.

The injection MUST occur at both normal activation dispatch and checkpoint-restored activation dispatch paths.
