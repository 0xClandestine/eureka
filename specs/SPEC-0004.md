## Abstract

Defines the `Edge` type — a directed typed connection between an output port on one node and an input port on another, including the semantics of feedback edges.

## Specification

### Edge

An `Edge` MUST contain:
- `from_node: String` — source node ID
- `from_port: String` — source output port name
- `to_node: String` — target node ID
- `to_port: String` — target input port name
- `feedback: bool` — whether this edge closes a cycle; defaults to `false` when absent in the manifest

An edge MUST be directed: it flows from `from_node.from_port` to `to_node.to_port`. Reverse traversal is not supported.

`source_id()` MUST return `"{from_node}.{from_port}"`.
`target_id()` MUST return `"{to_node}.{to_port}"`.

### Forward edges

An edge where `feedback == false` is a forward edge. The scheduler MUST deliver the artifact emitted on this edge to the target node in the same round as the emitting activation (see SPEC-0009).

### Feedback edges

An edge where `feedback == true` is a feedback edge. Feedback edges close cycles in the graph. The scheduler MUST deliver the artifact emitted on a feedback edge to the target node in round `N+1`, where `N` is the round of the emitting activation.

Feedback edges MUST be excluded from source-node detection (see SPEC-0006). A node that receives inputs only via feedback edges MUST still be treated as a source node that accepts the initial goal injection.

### Kind constraint

The `ArtifactKind` emitted on `from_port` MUST equal the `ArtifactKind` expected on `to_port`. This is enforced statically by graph validation (see SPEC-0007) before any node is executed.

## Rationale

Separating feedback edges from forward edges is necessary for correct round counting and source-node detection in cyclic graphs. Without this distinction, every node in a cycle would appear to have inbound edges and none would receive the initial goal injection.
