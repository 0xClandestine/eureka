## Abstract

Defines the YAML manifest format for declaring graph topology, LLM agents, and control nodes, and specifies how the manifest is loaded and converted to a `GraphSpec`.

## Specification

### GraphManifest

A `GraphManifest` is a YAML document with the following fields:
- `name: Option<String>` — optional human-readable graph name
- `description: Option<String>` — optional description
- `agents: Vec<AgentSpec>` — LLM-backed agent definitions; defaults to empty
- `control: Vec<ControlSpec>` — subprocess-backed control node definitions; defaults to empty
- `edges: Vec<Edge>` — directed edges; defaults to empty
- `metadata: serde_json::Value` — optional metadata; defaults to null

### AgentSpec

An `AgentSpec` declares one LLM agent. It MUST contain:
- `id: String` — unique node ID within the graph; also used as the `kind` string in the registry
- `prompt: String` — path to the system prompt file (Markdown); resolved relative to the YAML file
- `inputs: Vec<PortDef>` — input port declarations; defaults to empty
- `outputs: Vec<PortDef>` — output port declarations; defaults to empty
- `config: serde_json::Value` — per-agent LLM configuration overrides; defaults to empty object
- `tools: Vec<ToolSpec>` — shell tools available to the agent; defaults to empty
- `output_schema: serde_json::Value` — JSON Schema the agent's `submit` call MUST conform to

`description: Option<String>` MAY be present.

### ControlSpec

A `ControlSpec` declares one subprocess-backed control node. It MUST contain:
- `id: String` — unique node ID within the graph
- `kind: String` — the kind string used for registry lookup; MAY differ from `id`
- `command: Vec<String>` — subprocess argv; `command[0]` is the binary
- `inputs: Vec<PortDef>` — input port declarations; defaults to empty
- `outputs: Vec<PortDef>` — output port declarations; defaults to empty
- `config: serde_json::Value` — per-instance configuration; defaults to empty object
- `timeout_secs: u32` — subprocess wall-clock timeout; defaults to `60`

`description: Option<String>` MAY be present.

### ToolSpec

A `ToolSpec` declares a shell tool available to an agent. It MUST contain:
- `name: String` — tool name shown to the LLM; MUST NOT be `"submit"` (reserved)
- `description: String` — description shown to the LLM in the tool schema
- `command: Vec<String>` — subprocess argv
- `args_schema: serde_json::Value` — JSON Schema for the tool's arguments
- `timeout_secs: u32` — subprocess timeout; defaults to `30`

### Path resolution

`GraphManifest::load(path)` MUST:
1. Read and parse the YAML file at `path`
2. For each `AgentSpec`, resolve the `prompt` path relative to `path`'s parent directory
3. For each `ControlSpec` and `ToolSpec`, if `command[0]` is a relative path that resolves to an existing file when joined with the parent directory, replace it with the absolute path. If `command[0]` is a bare binary name (e.g. `python3`) or a relative path that does not resolve to a file on disk, it MUST be left unchanged so PATH lookup works at spawn time.

### Conversion to GraphSpec

`GraphManifest::to_graph_spec()` MUST produce a `GraphSpec` where:
- Each `AgentSpec` with `id = X` becomes a `GraphNodeSpec` with `id = X` and `kind = X`
- Each `ControlSpec` with `id = X` and `kind = K` becomes a `GraphNodeSpec` with `id = X` and `kind = K`
- All edges are transferred unchanged

### Loading errors

`GraphManifest::load` MUST return `GraphError::ParseError` if the file cannot be read or the YAML cannot be parsed.

## Rationale

Separating `id` from `kind` on control nodes allows multiple instances of the same plugin kind to coexist in one graph (e.g. two independent ranker nodes using the same `elo-ranker` kind but different configs).

Agent `id == kind` because agents are unique by definition — each preamble and port declaration is specific to that agent.
